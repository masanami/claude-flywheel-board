## 1. 前提の再確認

### 1.1 脅威モデル（既存決定の踏襲）

ローカル個人利用・127.0.0.1 固定バインド・Host/Origin 検証あり（`api.ts` の `isAllowedHost`/
`isAllowedOrigin`。HTTP・WS 共通）。この前提は変えない。

**ここから導かれる重要な帰結**: 「repo 内のディレクトリを symlink に差し替えられる主体」は
board サーバと同一ユーザー権限を持つローカルプロセスであり、その主体は board を経由せずに
同じ破壊・改変を直接実行できる。したがって書き込み経路の TOCTOU 対策で得られるのは
**権限の遮断ではなく、(a) 悪意のない symlink 構成（`docs -> ../shared-docs` のような通常の
運用）で board の書き込みが意図せず repo 外へ着弾することの防止**と、**(b) 多層防御**である。
この整理は §2 の方式選定（ネイティブ依存を足してまで完全性を追わない）の根拠になる。

なお読み取り経路の TOCTOU は §2.4（file-tree-non-md-support.md）で残余リスクとして受容済みで、
本設計はその非対称（書き込みは追加防御を持つ）を維持する。

### 1.2 再利用する既存資産（読み取り側 Phase A/B で実装済み）

| 資産 | 実装 | 書き込み側での扱い |
|------|------|------------------|
| `hasExcludedSegment` / `isExcludedSegment` | `md/path-validation.ts` | **そのまま共有**（要求パスの生セグメント検査） |
| `PREVIEWABLE_EXTENSIONS` | 同上 | **そのまま共有**（配置可能な拡張子の正本） |
| `validateMdPath` | 同上 | **DELETE のみ共有**（既存ファイルの適格性判定） |
| `PREVIEW_MAX_BYTES_BY_KIND` | `api.ts` | **そのまま共有**（配置サイズ上限。1MB/10MB） |
| 状態ファイル名の定数 | `watcher.ts`（`LEDGER_FILE_NAME` 等） | **deny-list の導出元**（§5） |

POST の対象パスは操作前に存在しないため `validateMdPath`（`realpathSync` 前提）は使えない。
「まだ存在しないパス」用の検証を新設し（§2.3）、上記の判定部品は共有する。

## 2. 論点1: 祖先ディレクトリの symlink 置換対策 — **(a) fd/cwd ベース検証を採用**

### 2.1 検証で確認した事実（付録 A）

- **脅威は実在する**: 検証済みパスの祖先ディレクトリを symlink へ差し替えると、パス名ベースの
  `open(O_CREAT|O_EXCL)`・`unlink` は repo 外の実体に着弾・到達する（A-2a / A-2b）。
- **Node 標準 fs に `openat`/`unlinkat`/`renameat`/`fchdir` は存在しない**（A-0a / A-7）。
- **fd → パスの逆引きは macOS では成立しない**: `/proc` が無く、`realpathSync('/dev/fd/N')` は
  `/dev/fd/N` を、`realpathSync.native` は `/dev/fd/<basename>` という**誤った値**を返す
  （A-3a〜A-3c）。「操作後に fd から実パスを引いて封じ込めを事後検証する」方式は
  **darwin では採用不能**。
- **`/dev/fd/<dirfd>/child` の相対解決も macOS では不可**（A-3d。ENOENT）。openat 代替として
  よく挙がる magic path 方式は **Linux 限定**であり、macOS を主対象とする board では
  プラットフォーム分岐が必須になる。
- **`process.chdir()` は openat 相当の保証を与える**（A-4b）。chdir 後の cwd はディレクトリの
  vnode を掴んだ状態で、その後に同じパス名を repo 外への symlink へ差し替えても、**相対パスでの
  作成・削除は掴んだディレクトリに着弾する**（`repo 外着弾=false / 掴んだ dir に着弾=true`）。
- **chdir 前の置換は inode 比較で検知できる**（A-4a / A-4d）。事前の逐次 `lstat` 降下で記録した
  `(dev, ino)` と、chdir 後の `statSync(".")` を突き合わせれば、降下〜chdir の間の差し替えを検知して
  中断できる。
- **最終要素は Node 標準で守れる**: `O_CREAT|O_EXCL` は最終要素が symlink なら `EEXIST` で失敗し
  （A-1a）、`O_NOFOLLOW` は `ELOOP`（A-1b）、`O_DIRECTORY|O_NOFOLLOW` は symlink ディレクトリを
  `ENOTDIR` で拒否する（A-3g）。

### 2.2 決定

> **(a) fd/cwd ベース検証を採用する。ネイティブ依存の追加 (b) は不採用。残余リスク (c) は §2.5 に明記して受容する。**

具体的な機構は「**逐次 `lstat` 降下による静的 symlink 拒否**」＋「**`process.chdir` による inode
ピン留め**」の 2 段構成とする。

(b) を採らない理由: openat を提供する保守された npm パッケージが存在せず、自前 N-API アドオンの
追加は `node-pty` に続く 2 つ目のネイティブ依存となり、ローカル GUI のセットアップ容易性
（`postinstall` ワークアラウンドを既に 1 件抱えている）を損なう。得られる差分は §1.1 のとおり
**権限利得のない攻撃者に対する完全性**のみで、費用対効果が見合わない。

### 2.3 採用する手順

```text
[検証フェーズ]  ※すべて同期・repo ルートは realpathSync 済み
 1. 要求パスの生セグメント列を検査（hasExcludedSegment: "." 始まり・node_modules・".."）
 2. deny-list 判定（§5）
 3. 拡張子アローリスト判定（PREVIEWABLE_EXTENSIONS。POST は必須 / DELETE は validateMdPath 経由）
 4. repo ルートから親ディレクトリまでを 1 セグメントずつ lstat で降下
    - symlink → 拒否（＝暗黙 mkdir も無いので、途中の不存在も拒否）
    - ディレクトリでない → 拒否
    - 最後に親ディレクトリの (dev, ino) を記録
[クリティカルセクション]  ※await を挟まない完全同期。ここで初めて副作用を起こす
 5. process.chdir(親ディレクトリの絶対パス)
 6. statSync(".") の (dev, ino) が 4 の記録と一致するか検証（不一致なら中断）
 7. 相対パス（basename のみ）で実操作
    - POST:   openSync(basename, O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW, 0o644) → writeSync → closeSync
    - DELETE: lstatSync(basename) でディレクトリを除外 → unlinkSync(basename)
 8. finally で process.chdir(元の cwd) を復元
```

ステップ 6 が通れば「cwd はステップ 4 で *repo ルートから symlink を 1 つも経由せずに到達できることを
確認した* ディレクトリ inode そのもの」であることが確定する。以降ステップ 7 の相対パス操作では
祖先パスの再解決が起こらないため、**祖先 symlink 置換は構造的に無効化される**。

### 2.4 `process.chdir` の副作用と、その封じ込め

`process.chdir()` はプロセス全体に効く可変状態であり、サーバに持ち込むのは本来避けたい。
検証で分かった性質と、それに対する設計上の手当ては次のとおり。

| 性質 | 検証結果 | 手当て |
|------|---------|--------|
| クリティカルセクション中に他の JS が割り込むか | **割り込まない**（A-2 系 poc2-2。完全同期のため） | セクション内に `await` を置かない規約をコメントとテストで固定する。ロック機構は不要 |
| 所要時間（イベントループ阻害） | chdir 1 回 **0.0011ms** / 10MB 同期 write **1.48ms** | 人間操作起点の低頻度操作であり、10MB 上限下では実用上無視できる |
| **飛行中の非同期 fs が相対パスだと影響を受けるか** | **受ける**（64 件中 43 件が変更後 cwd で解決） | **不変条件が必要**（下記） |
| chdir 済み cwd が削除された場合 | 相対 create は `ENOENT` で安全に失敗 | 500 として扱う |

**必要な不変条件: board サーバは fs 操作に相対パスを一切使わない。**
コード調査の結果、現状で唯一この不変条件を破りうるのは `loadFleetManifest` が返す
`FleetEntry.path` である（`manifest.ts` は「手書き fleet.tsv に相対パスが使われている可能性を
否定できない」として相対パスを許容し続けており、`appendFleetEntry` 経由の追加のみ絶対パスを
強制している）。相対の `entry.path` は `watcher.ts` の `ledgerPathFor` 等を経由して
`parsers/journal.ts`・`parsers/runs.ts` の**非同期** `readFile` へ相対パスのまま渡る。
その他の経路（`api.ts` の `validation.resolvedPath`、`serveStatic` の `UI_DIST_ROOT`、
`resolveFleetManifestPath`、`fs.globSync({ cwd: entry.path })`）は絶対パスか同期 API のため影響しない。

→ **実装フェーズ W0（§7）で `parseFleetManifestContent` が `entry.path` を絶対化する**。
起動時 1 回・起動時 cwd 基準の `path.resolve` であり、相対パスの既存 fleet.tsv は「それまで
暗黙に意味していた解決結果」に固定されるだけで後方互換は壊れない。

### 2.5 残余リスク（受容）

1. **検証済みディレクトリ実体の移動＋同名 symlink 差し替え**: 降下検証と chdir の間に、攻撃者が
   検証済みディレクトリを repo 外へ `mv` し、同じパス名に移動先への symlink を置くと、chdir は
   symlink を辿って**同一 inode** に着地するため、ステップ 6 の inode 比較では検知できない
   （A-6 で実測）。結果として repo 外になったディレクトリへ書き込む。
   受容根拠: この操作を行える主体は §1.1 のとおり board を介さず同じことができ、権限利得がない。
   また「掴んだディレクトリオブジェクトに対して操作する」という結果自体は、開いた fd の意味論
   （openat/ネイティブ依存でも同じ）と一致しており、方式を変えても解消しない。
2. **fleet.tsv の repo ルートそのものが symlink 経由の場合**: ルートは `realpathSync` で 1 回解決
   してから降下を始めるため、ルート自体の symlink は許容される（読み取り側と同じ扱い）。
   ルートを差し替えられた場合の保護は無い（読み取り経路と同じ残余リスク）。
3. **Windows ネイティブ**: `O_NOFOLLOW` 等の意味論が POSIX と異なるため対象外（§3.4 と共通）。

## 3. 論点2: 削除の inode 同一性 — **保証すべき不変条件を再定義して受容範囲を確定**

### 3.1 決定

> **「削除した inode が lstat した inode と同一であること」は保証しない（できない）。保証する不変条件を
> 「削除対象は、検証済み親ディレクトリ直下の、要求されたその名前である」＝**封じ込めの保証**に再定義する。**

### 3.2 根拠

1. **inode 指定の削除 API は POSIX に存在しない**。`unlinkat(dirfd, name, 0)` も *名前* 指定であり、
   ディレクトリ fd を固定できるだけで「この inode を消す」ことはできない。**Node 標準 fs の欠落では
   なく POSIX の設計**であり、ネイティブ依存 (b) を足しても解決しない（A-6a / A-7）。
   したがって「保証方式を定義する」という選択肢は**そもそも実現不能**である。
2. 一方、**危険なのは「どのディレクトリの名前を消すか」**（＝祖先経路の同一性）であり、これは §2 の
   chdir による inode ピン留めで**保証できる**。repo 外のファイルを削除する経路は塞がる。
3. 残るのは「検証〜`unlink` の間に *同一の検証済みディレクトリ内で* 同名エントリが別ファイルへ
   差し替わり、差し替え後を削除する」ケースのみ。影響範囲は**検証済み repo 内・要求どおりのパス**に
   限定される。これは `rm <path>` を含むあらゆるパス名指定の削除が持つ性質と同じで、権限利得もない。

### 3.3 併せて確定する削除の意味論

- **symlink エントリの削除は許可する**。`unlink` は symlink 自体のみを除去し、リンク先の実体は
  残る（A-1c で実測）。リンクは検証済み親ディレクトリ直下＝repo 内にあるため封じ込めは保たれ、
  「ツリーに出る＝削除できる」の対称性（読み取り側 §2.2 の方針）も保てる。
- **ディレクトリの削除は対象外**（Issue #144 のスコープどおり）。クリティカルセクション内の
  `lstatSync(basename)` で `isDirectory()` なら拒否する。
- **OS ゴミ箱は使わない**（§8 決定 7）。macOS の実ゴミ箱は `osascript`（Finder 自動化権限の
  プロンプト）か追加ネイティブ依存を要し、WSL2 にはデスクトップゴミ箱が無い。board 独自の
  ゴミ箱ディレクトリ（rename ベース。同一ボリューム内なので原子的に可能なことは A-6b で確認済み）は
  repo に git 追跡外のゴミが溜まる新しい問題（保持期間・GC・deny-list）を作る。**確認ダイアログ＋
  対象パスの明示**で不可逆性に対処し、実運用でデータ喪失が起きたら再評価する（YAGNI）。

### 3.4 受容範囲の明記（Issue #144 の必須要件への回答）

| 項目 | 内容 |
|------|------|
| **対応プラットフォーム** | macOS（darwin）／Linux（WSL2 含む）。POSIX の `unlink`・`O_NOFOLLOW`・`chdir` 意味論に依存する。Windows ネイティブは非対応（board は元々 macOS/WSL2 前提。README 参照） |
| **残余リスク** | 検証〜`unlink` の間に同名エントリが差し替わった場合、差し替え後のファイルを削除する。影響は**検証済み repo 内の要求どおりのパス**に限定され、repo 外へは波及しない |
| **同時操作の制約** | board からの削除・配置と、同一パスに対する repo 内での並行 rename／再作成（他エージェントの `run-cycle`・エディタの保存等）を同時に行わないこと。board の書き込みは人間の明示操作起点でありサイクル自走とは独立のため、運用上この制約は満たしやすい |
| **保証されること** | repo ルート外の削除・書き込みが起きないこと（§2.3 のステップ 4〜7）。状態ファイルが削除・上書きされないこと（§5） |

## 4. 論点3: API 契約

### 4.1 エンドポイント

```text
POST /api/files?repo=<name>&path=<repo相対パス>
  Content-Type: application/octet-stream   # 本文はファイルのバイト列そのもの
  Origin: <必須>                            # 非ブラウザ直叩きの CSRF 面を狭める（§4.3）
  → 201 { path: string, kind: PreviewableKind, size: number }
  → 400 / 403 / 404 / 409 / 413 / 415 / 500（§4.2）

DELETE /api/files?repo=<name>&path=<repo相対パス>
  Origin: <必須>
  → 204 No Content
  → 400 / 403 / 404 / 500（§4.2）
```

- **ルート名は `/api/files`**（`/api/md/*` ではない）。`md` プレフィックスは読み取り系の歴史的名称
  として維持する決定済み（file-tree-non-md-support.md §3）だが、**新設の書き込み系にまでその歴史を
  引き継ぐ理由はない**。読み取りと書き込みで許可条件が異なる（deny-list の有無）ことを URL でも
  分離しておく。
- **リクエストの `Content-Type` は判定に使わない**。kind は読み取り側と同一に**拡張子アローリスト
  だけ**で決める（内容スニッフィングをしないという §2.3 の方針の裏返し。クライアント申告の
  MIME を信用する経路を作らない）。
- **暗黙 mkdir はしない**。親ディレクトリが存在しなければ 404。
- **上書きフラグは実装しない**（§8 決定 3）。既存パスへの POST は常に 409。

### 4.2 エラーコード体系

既存 file/raw API の「理由を問わず一様に 404」方針は**存在有無を漏らさない**ことが目的である。
書き込み系は UI が実行可能なアクション（別名にする・別の場所に置く）を提示できる必要があるため、
次の原則で最小限だけ区別する。

> **場所の適格性に関わる失敗はすべて 404 に一様化する。区別してよいのは (i) 要求そのものの性質から
> 決まるもの（415・413）、(ii) 静的なポリシー（403 deny-list。パス文字列だけで決まり存在を漏らさない）、
> (iii) 適格と確定した場所での状態（409）に限る。**

| コード | 契機 | 本文 |
|--------|------|------|
| 400 | `repo`/`path` クエリの欠落・非文字列 | `{ error: "..." }` |
| 403 | Host/Origin 不正（既存ミドルウェア）／**Origin ヘッダ欠落**／**deny-list 該当** | `{ error: "..." }` |
| 404 | repo 名不明・親ディレクトリ不存在・親が非ディレクトリ・**祖先に symlink**・除外セグメント（`.`始まり/`node_modules`/`..`）・封じ込め違反・(DELETE) 対象不存在または通常ファイル/symlink 以外 | `{ error: "対象のパスが見つかりません" }`（**理由を分岐させない一様メッセージ**） |
| 409 | (POST) 同名が既に存在（`O_EXCL` の `EEXIST`） | `{ error: "同名のファイルが既に存在します: <path>" }` |
| 413 | サイズ超過（`PREVIEW_MAX_BYTES_BY_KIND[kind]`。text 1MB / image 10MB） | `{ error: "..." }` |
| 415 | 拡張子が `PREVIEWABLE_EXTENSIONS` 外 | `{ error: "この拡張子は配置できません: <ext>" }` |
| 500 | 検証通過後の I/O 失敗（`ENOSPC`・`EACCES`・chdir 後の `ENOENT` 等） | `{ error: "..." }`＋サーバログ |

**判定順序（漏洩防止のため固定する）**: パラメータ(400) → deny-list(403) → 除外セグメント・
封じ込め・親ディレクトリ検証(404) → 拡張子(415) → `Content-Length` と kind 別上限(413。**本文を
バッファする前**) → 本文読み込み → 実バイト長の再検査(413) → 実操作(409/500)。

応答本文の形は `POST /api/fleet/agents`（既存の書き込み系）に合わせて `{ error: string }` の JSON で
統一する（読み取り系の `c.text("Not Found", 404)` とは異なるが、UI がメッセージを表示する必要が
あるため。404 のメッセージを一様にすることで漏洩防止は維持される）。

**受容する軽微な情報露出**: 「親ディレクトリが存在するか」は 404 と 415/413/409 の差から推定できる。
ツリーに現れないディレクトリ（プレビュー可能なファイルを含まない空ディレクトリ等）の存在が
分かる程度で、脅威モデル（同一ユーザーが `ls` できる）の下では実害がない。

### 4.3 サイズ上限と本文の扱い

- 外側の絶対上限として `hono/body-limit`（追加依存なし・確認済み）を `/api/files` の POST にのみ
  適用し、`maxSize` は `PREVIEW_MAX_BYTES_BY_KIND` の最大値（10MB）とする。
- kind 別の上限は拡張子分類の**後**に適用する（読み取り側 file API と同一の順序・同一の定数を共有し、
  「置けるがプレビューできない」「プレビューできるが置けない」の非対称を作らない）。
- `Content-Length` が無い（chunked）要求は body-limit の実バイト計上で 413 に落ちる。

### 4.4 Origin ヘッダ必須化

Fetch 仕様上、ブラウザは GET/HEAD 以外のリクエストに同一オリジンでも `Origin` を付与する。
したがって書き込み系 2 本に限り **`Origin` の欠落を 403 で拒否**しても board UI は動作し、
`curl` 等の非ブラウザ直叩きの面だけを狭められる。既存の `POST /api/fleet/agents` は
Origin 欠落を許容しているが、本 Issue のスコープ外として**変更しない**（別途フォローアップ候補）。

## 5. 論点4: deny-list（NFR-01 のコード強制）

### 5.1 対象パターン

repo ルートからの相対パスに対して判定する。**判定は要求パスの生セグメント列に対して行い、
DELETE では `validateMdPath` が返す解決後の相対パスにも同じ判定を適用する**（通常名 symlink 経由の
迂回を塞ぐ。要求パス側の検査だけでは `notes.md -> challenge-ledger.md` を落とせない）。

| 種別 | パターン | 由来 |
|------|---------|------|
| ルート直下の完全一致 | `challenge-ledger.md` | `watcher.ts` `LEDGER_FILE_NAME` |
| ルート直下の完全一致 | `priority-policy.md` | `watcher.ts` `PRIORITY_POLICY_FILE_NAME` |
| ルート直下の正規表現 | `/^challenge-archive.*\.md$/` | `watcher.ts` の台帳アーカイブ |
| ルート直下の完全一致 | `fleet.tsv` | NFR-01（board 自身の manifest。repo ルートが `~/.flywheel` の場合への防御） |
| 先頭セグメント一致（配下すべて） | `journal/` | `watcher.ts` `JOURNAL_FILE_NAME` の親 |
| 先頭セグメント一致（配下すべて） | `memory/` | NFR-01・CLAUDE.md のドメイン記憶 |
| 先頭セグメント一致（配下すべて） | `.flywheel/`（`runs.jsonl` を含む）・`.git/` | NFR-01・`watcher.ts` `RUNS_FILE_NAME` |

`.flywheel/`・`.git/` は `isExcludedSegment` の `.` 始まり判定によって既に構造的に到達不能だが、
**deny-list にも重複して明示的に登録する**（片方の判定が将来変更されても保護が消えないようにする。
deny-list の判定を除外セグメント判定より前に置く理由でもある）。

### 5.2 ドリフト防止

- deny-list の定義は**`watcher.ts` が export する定数から導出**する（文字列リテラルを複製しない）。
  読み取り側で `PREVIEWABLE_EXTENSIONS` を単一正本にしたのと同じ方針。
- **不変条件テスト**を必須の受け入れ基準にする: `ledgerPathFor` / `journalPathFor` / `runsPathFor` /
  `priorityPolicyPathFor` / `archiveGlobFor` が指す repo 相対パスが、すべて deny-list で拒否される
  こと。将来 board が新しい状態ファイルを監視対象に加えたとき、このテストが deny-list の追加漏れを
  検出する（＝NFR-01 の自動的な番人になる）。
- 加えて「`src/server` 配下に状態ファイルへの書き込み経路が無いこと」という既存のレビュー観点
  （CLAUDE.md 品質方針）は、本機能で書き込み API が増えるため**レビュー時に必ず確認する**。

### 5.3 拡張子アローリストとの関係

`challenge-ledger.md` 等は `.md`＝プレビュー可能拡張子であり、**アローリストでは防げない**。
deny-list はアローリストの後段ではなく**前段**（判定順序 §4.2）に置く。

## 6. 論点5: UI 設計

### 6.1 配置（D&D）

- **ドロップ先**: `FileTree` の repo ノードとディレクトリノード。`onDragOver` で `preventDefault()`＋
  `dataTransfer.dropEffect = "copy"`、ホバー中のノードをハイライトする。
- **制約（明記する）**: ツリーのディレクトリはフラットなファイル一覧から導出されるため、
  **プレビュー可能なファイルを 1 つも含まないディレクトリはツリーに現れず、ドロップ先にもできない**。
  暗黙 mkdir をしない決定と併せて、「置ける場所＝ツリーに見えている場所」に揃える。
- **複数ファイル**: 許可する。**1 件ずつ直列に POST** する（サーバのクリティカルセクションを
  単純に保ち、ファイルごとに成否を出せるようにするため）。結果はツリー上部のステータス行に
  「n 件配置 / m 件失敗（理由）」で表示する。
- **ディレクトリのドロップ**: `dataTransfer.items[i].webkitGetAsEntry()?.isDirectory` で検出し、
  送信前に「ディレクトリは配置できません」として拒否する（再帰アップロードは非対応）。
- **成功後**: `FileTree` 内部のリフレッシュトークンを進めて `GET /api/md/tree` を再取得する
  （既存の `refreshToken` prop と OR で合流させ、リフレッシュボタンの経路は変えない）。

### 6.2 配置（ペースト）

- ツリーコンテナの `paste` イベントで `clipboardData.files` を取得する。
- **貼り付け先**: 直前にクリックしたディレクトリ／repo ノード（`pasteTargetKey`。未選択なら
  ペースト操作自体を無効化し「貼り付け先のフォルダを選択してください」と案内する）。
  現在の選択ハイライト（`selectedKey`。ファイル用）とは別の状態として持つ。
- **ファイル名**: スクリーンショットのペーストは名前が `image.png` 固定または空になるため、
  名前が空・拡張子が無い場合は MIME から拡張子を引いて
  `pasted-<YYYYMMDD-HHmmss>.<ext>` を生成する（衝突を実質的に回避する）。
  名前が取れる場合はそのまま使う（サーバ側の検証に委ねる）。

### 6.3 上書き拒否（409）時の挙動

**自動リネームはしない**。「同名のファイルが既に存在します: `<repo>/<path>`」をステータス行に
表示して終了する。ユーザーが意図しない別名で保存されるより、明示的に失敗する方が安全
（ペーストは §6.2 のタイムスタンプ名で衝突しないため、実際に踏むのは D&D の明示的な同名投入のみ）。

### 6.4 削除

- **起動**: ファイルノードの右クリック（コンテキストメニュー）＋**フォーカス中のファイル行での
  `Delete`/`Backspace` キー**（既存の `handleTreeKeyDown` に合流。マウス専用にしない）。
- **確認ダイアログ（必須）**: `repo` 名と repo 相対パスを**省略せず**表示する。
  既定フォーカスは「キャンセル」に置き、`Escape` で閉じられること。
- **成功後（204）**: ツリーを再取得し、削除したファイルが現在プレビュー中だった場合は
  `PreviewPanel` の選択状態と表示内容を明示的にクリアする（新規 prop `onFileDeleted` で通知）。
  `md_subscribe` 中の場合は chokidar の `unlink` も `md_file_changed` を送るが（`md/watch.ts`）、
  それに任せると再フェッチが 404 になり「取得失敗」表示になるため、UI 側で先にクリアする。
- **失敗時**: ステータス行にサーバのメッセージを表示する（deny-list なら 403 のメッセージが出る）。

### 6.5 UI が deny-list を持たないこと

削除不可・配置不可の判定は**サーバのみが正本**とし、UI に deny-list を複製しない
（読み取り側で「kind の正本は file API のみ」としたのと同じ理由）。そのため board 上では
`challenge-ledger.md` にも削除メニューは出るが、実行すると 403 とその理由が表示される。

## 7. 論点6: 実装フェーズ分けと受け入れ基準

### 7.1 フェーズ分け（1 フェーズ = 1 PR。≤400 行を目安）

| # | 内容 | 主な受け入れ基準 |
|---|------|----------------|
| **W0** | `parseFleetManifestContent` が `entry.path` を絶対化する（§2.4 の不変条件の前提整備） | 相対パスの fleet.tsv が起動時 cwd 基準で絶対化されること／既存の重複比較・テストが壊れないこと |
| **W1** | 書き込みガード基盤 `src/server/md/write-guard.ts`（deny-list・降下検証・chdir クリティカルセクション）。API 未公開 | §7.2 のテスト全件 |
| **W2** | `POST /api/files`＋UI の D&D／ペースト | 契約（201/400/403/404/409/413/415）／UI の直列送信・ディレクトリ拒否・409 表示 |
| **W3** | `DELETE /api/files`＋UI のコンテキストメニュー・確認ダイアログ・キーボード起動 | 契約（204/400/403/404）／確認ダイアログ必須／プレビュー中ファイル削除時のクリア |

**配置（W2）を削除（W3）より先に置く**理由: `O_CREAT|O_EXCL` により配置は既存データを絶対に
破壊しない（最悪でも新規ファイルが 1 つできるだけ）ため、不可逆な削除はガード基盤が
W2 で実運用に晒された後に投入する方が安全。

### 7.2 テストの受け入れ基準（W1 で全件・§4 §5 の各層に対応）

ガード基盤は **`verifyWritableParent()`（検証フェーズ）と `runInVerifiedParent()`
（クリティカルセクション）の 2 関数に分けて export する**。両者は本番ハンドラでは同期的に
連続で呼ばれるが、テストからは間に任意の操作を挟めるため、**TOCTOU シナリオを本番コードに
テスト専用フックを埋めずに再現できる**（クリティカルセクションが完全同期であるがゆえに、
この分割が唯一の再現手段になる）。

| # | シナリオ | 期待 |
|---|---------|------|
| 1 | 正常系（配置・削除） | 201 / 204 |
| 2 | **最終要素が symlink**（配置） | `EEXIST` → 409（実体は変更されない） |
| 3 | **最終要素が symlink**（削除） | リンクのみ消え、リンク先実体が残る |
| 4 | **祖先ディレクトリが静的に symlink**（配置・削除） | 404（降下検証で拒否） |
| 5 | **祖先ディレクトリの TOCTOU 置換**（`verifyWritableParent` 後・`runInVerifiedParent` 前に差し替え） | inode 不一致で中断、または元ディレクトリに着弾。**repo 外に一切副作用が無いこと**を両方の観点で検査 |
| 6 | **親ディレクトリの TOCTOU 置換（chdir 後）** | 相対操作が元ディレクトリに着弾し、repo 外に副作用が無い |
| 7 | 親ディレクトリ不存在／親がファイル | 404（暗黙 mkdir をしない） |
| 8 | 除外セグメント（`..`・`.hidden`・`node_modules`。`..` で消えるケースを含む） | 404 |
| 9 | **deny-list 不変条件テスト**（§5.2） | `watcher.ts` の全監視パスが拒否される |
| 10 | deny-list への配置・削除（`challenge-ledger.md`・`journal/x.md`・`memory/x.md`） | 403 |
| 11 | 解決後パスが deny-list（`notes.md -> challenge-ledger.md` の削除） | 403 |
| 12 | 拡張子アローリスト外（`.pem`） | 415 |
| 13 | サイズ超過（text 1MB 超・image 10MB 超） | 413（本文を書き込まない） |
| 14 | 同一パスへの並行 POST 2 本 | 一方が 201・他方が 409（`O_EXCL` の排他） |
| 15 | **cwd 復元**（成功時・例外時の両方） | 操作後に `process.cwd()` が元に戻る |
| 16 | Origin ヘッダ欠落 | 403 |

テストは実ファイル（`fs.mkdtempSync` の一時ディレクトリ）で行う。CLAUDE.md のテスト方針
（状態ファイルの読み取りはフィクスチャの実ファイル）と整合し、symlink 置換は実 fs でしか
検証できないため mock しない。

## 8. 置いた仮定・意思決定（サマリ）

| # | 決定 | 根拠 |
|---|------|------|
| 1 | 祖先 symlink 対策は **(a) fd/cwd ベース検証**（逐次 `lstat` 降下＋`process.chdir` inode ピン留め＋相対パス操作）。ネイティブ依存 (b) は不採用 | macOS では fd→パス逆引きも `/dev/fd` 相対解決も不可（A-3）。chdir は openat 相当の保証を portable に与える（A-4）。§1.1 より権限利得のない攻撃者に対する完全性に費用を払わない（§2.2） |
| 2 | 削除の inode 同一性は**保証しない**。不変条件を「封じ込め」に再定義し、対応プラットフォーム・残余リスク・同時操作制約を §3.4 に明記して受容 | inode 指定の削除 API は POSIX に存在せず（`unlinkat` も名前指定）、ネイティブ依存でも解決しない。危険な「どのディレクトリか」は決定 1 で保証済み（§3.2） |
| 3 | **上書きフラグは実装しない**（既存パスへの POST は常に 409） | Issue の「デフォルト拒否」より厳格側。一時ファイル→`rename` 経路（既存データを破壊しうる唯一の操作）を作らずに済む。YAGNI |
| 4 | ルート名は **`/api/files`**（`/api/md/*` に載せない） | 読み取り系の歴史的名称を書き込み系へ引き継ぐ理由がなく、許可条件が異なることを URL でも分離する |
| 5 | エラーは「場所の適格性 → 一様 404 / 静的ポリシー → 403 / 要求の性質 → 415・413 / 適格な場所の状態 → 409」で最小限だけ区別 | 読み取り側の非漏洩方針を保ちつつ、UI が次の行動を提示できるようにする（§4.2） |
| 6 | deny-list は `watcher.ts` の定数から**導出**し、全監視パスが拒否されることを不変条件テストで固定 | NFR-01 の自動的な番人にする。文字列の複製はドリフトの温床（§5.2） |
| 7 | **OS ゴミ箱は使わない**。確認ダイアログ＋対象パス明示で不可逆性に対処 | macOS は Finder 自動化権限か追加依存が必要・WSL2 にはデスクトップゴミ箱が無い。board 独自ゴミ箱は保持期間/GC/deny-list の新問題を生む（§3.3。YAGNI） |
| 8 | 配置可能な拡張子・サイズ上限は**読み取り側の定数をそのまま共有** | 「置けるがプレビューできない」非対称を作らない（Issue #144 のガード方針） |
| 9 | UI に deny-list を複製せず、サーバのエラーメッセージを表示する | 種別判定の正本をサーバに一本化した読み取り側と同じ方針（§6.5） |
| 10 | 409 時に**自動リネームしない** | 意図しない別名保存より明示的失敗が安全。ペーストはタイムスタンプ名で衝突しない（§6.3） |
| 11 | **W0（`entry.path` の絶対化）を前提整備として先行実装**する | chdir 方式は「サーバが相対パスの非同期 fs を発行しない」ことに依存し、現状唯一の違反候補が相対 `entry.path` だから（§2.4） |
| 12 | 書き込み系 2 本のみ **Origin 必須**。既存 `POST /api/fleet/agents` は変更しない | 非ブラウザ直叩きの面を狭める。既存エンドポイントの挙動変更は本 Issue のスコープ外 |
| 13 | 実装は **W0 → W1（ガード基盤）→ W2（配置）→ W3（削除）** の 4 PR | 破壊しない配置を先に実運用へ晒し、不可逆な削除を後段に置く（§7.1） |

## 9. 未検証事項

- **実ブラウザでの `Origin` 付与**（§4.4）。Fetch 仕様上 GET/HEAD 以外には付与されるが、jsdom
  ベースの既存テストでは実挙動を確認できない。W2 実装時に実ブラウザで確認し、付与されない
  ケースが見つかった場合は Origin 必須化を撤回する（`isAllowedOrigin` の既存判定のみに戻す）。
- **Linux/WSL2 上での §2 の挙動**。付録 A の検証は darwin のみで実施した。`chdir`＋相対操作・
  `O_CREAT|O_EXCL`・`O_NOFOLLOW` はいずれも POSIX 標準の意味論であり差は想定されないが、
  W1 のテストを WSL2 でも 1 度通して確認する。
- **10MB 同期 write のネットワークボリューム上での所要時間**。ローカル APFS では 1.48ms だが、
  ネットワークマウントされた repo では長くなる。実測して問題が出れば、書き込みだけを
  クリティカルセクション外（fd 取得後の非同期 write）へ出す設計変更を検討する
  （fd を掴んだ後なら cwd 復元後でも安全なため、変更自体は小さい）。
- ペースト時の `clipboardData.files` の挙動差（Safari/Chrome、スクリーンショット vs Finder コピー）。

## 付録 A: 実現可能性の検証結果

Node v24.18.0 / darwin 25.5.0 上で、一時ディレクトリに repo 相当の構造を作って実測した結果
（再現用の最小コードは A-末尾）。

| # | 確認事項 | 結果 |
|---|---------|------|
| A-0a | `fs` に `openat`/`unlinkat`/`renameat` 系があるか | **無い**（`at` で終わるのは `fstat`/`lstat`/`stat` のみ） |
| A-0b | 利用可能な `open` フラグ | `O_NOFOLLOW=256` `O_DIRECTORY=1048576` `O_SYMLINK=2097152` / **`O_PATH` は undefined**（darwin） |
| A-1a | `O_CREAT|O_EXCL` で最終要素が symlink | **`EEXIST` で拒否**（作成されない） |
| A-1b | `O_NOFOLLOW` で既存 symlink を open | **`ELOOP` で拒否** |
| A-1c | symlink に対する `unlink` | **リンクのみ消え、リンク先実体は残る** |
| A-2a | 祖先を symlink へ置換 → パス名 `open(O_CREAT|O_EXCL)` | **repo 外に着弾する**（脅威は実在） |
| A-2b | 祖先を symlink へ置換 → パス名 `unlink` | **repo 外のファイルを削除できる** |
| A-3a | `realpathSync('/dev/fd/N')` | `/dev/fd/11`（**実パスにならない**） |
| A-3b | `realpathSync.native('/dev/fd/N')` | `/dev/fd/probe.txt`（**誤った値**。fd→パス逆引きに使えない） |
| A-3c | `realpathSync('/proc/self/fd/N')` | `ENOENT`（macOS に `/proc` は無い） |
| A-3d | `/dev/fd/<dirfd>/child` の相対解決 | **`ENOENT`（openat 代替に使えない。Linux 限定の手法）** |
| A-3f | dirfd の `fstat` で `(dev, ino)` | 取得可（`isDirectory()=true`） |
| A-3g | `O_DIRECTORY|O_NOFOLLOW` で symlink ディレクトリ | **`ENOTDIR` で拒否** |
| A-4a | `chdir(検証済み dir)` 後の `statSync(".")` と dirfd の `(dev,ino)` | **一致**（同一性を確認できる） |
| A-4b | chdir 後に祖先パス名を repo 外 symlink へ置換 → 相対 `open(O_CREAT|O_EXCL)` | **repo 外着弾=false / 掴んだ dir に着弾=true**（＝openat 相当の保証） |
| A-4d | 置換**後**に chdir した場合の `statSync(".")` | 検証済み inode と**不一致**（＝検知できる） |
| A-4e | 相対 `unlink` も掴んだ cwd 基準か | **そのとおり** |
| A-5 | 飛行中の**相対パス**非同期 `readFile` 64 件に対する chdir の影響 | **21 件が旧 cwd・43 件が新 cwd で解決**（＝影響を受ける。§2.4 の不変条件の根拠） |
| A-6 | 検証済み dir を repo 外へ `mv` ＋同名 symlink 差し替え後の chdir | **inode 一致（＝検知できない）**。§2.5 の残余リスク 1 |
| A-6b | 同一ボリューム内 `rename` によるゴミ箱化 | 可能（ただし §3.3 の決定により採用しない） |
| A-7 | `fs.fchdir` / `fs.openat` | いずれも `undefined` |
| — | クリティカルセクション中の他タスク割り込み | **無し**（完全同期のため `setImmediate` が発火しない） |
| — | `chdir` 1 回の所要 | 約 **0.0011ms** |
| — | 10MB の同期 `write` の所要 | 約 **1.48ms**（ローカル APFS） |
| — | 削除済み cwd への相対 `open(O_CREAT)` | `ENOENT`（安全に失敗） |

再現の要点（実装時はこの形をガード基盤の骨格にする）:

```js
// 検証フェーズ（同期）: repo ルートから親まで lstat で降下し symlink を拒否、(dev,ino) を記録
let cur = fs.realpathSync(repoRoot);
for (const seg of requestSegments.slice(0, -1)) {
  cur = path.join(cur, seg);
  const st = fs.lstatSync(cur);            // 追従しない
  if (st.isSymbolicLink() || !st.isDirectory()) throw new NotFound();
}
const expected = fs.lstatSync(cur);

// クリティカルセクション（await を挟まない完全同期）
const saved = process.cwd();
try {
  process.chdir(cur);
  const here = fs.statSync(".");
  if (here.dev !== expected.dev || here.ino !== expected.ino) throw new NotFound();
  const fd = fs.openSync(basename, O_CREAT | O_EXCL | O_WRONLY | O_NOFOLLOW, 0o644);
  try { fs.writeSync(fd, bytes); } finally { fs.closeSync(fd); }
} finally {
  process.chdir(saved);
}
```
