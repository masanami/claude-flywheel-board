# ファイルツリーの md 以外対応 — 調査・設計ドラフト

> **状態: 設計ドラフト（実装未着手）**。Issue #117 の検討スコープ 1（表示・プレビュー対応）の実現可能性調査と段階分け設計案、およびスコープ 2（D&D/コピペ配置・削除）の別 Issue 切り出し案をまとめる。本ドキュメントのマージは Issue #117 の完了を意味しない（実装着手・スコープ確定は人間判断）。Refs #117

## 概要

プレビューパネルのファイルツリー（docs/features/markdown-preview.md）は現在 `.md` のみを表示・プレビュー対象とする。実利用では設定・ログ・画像・ソースコード等もツリーから確認したい場面があるため、対応拡大の変更点・セキュリティ影響・段階分けを設計する。

## 1. 現行実装の調査結果（#61/#65 走査・除外、#63 パス検証、#66 file API）

### 1.1 拡張子チェックの所在（変更点の全量）

`.md` 制約は **`src/server/md/path-validation.ts` の `MD_EXTENSION` 定数を単一の正本**として、以下の 3 経路が共有している（#63 の申し送りで判定基準のドリフト防止のため一元化済み）:

| 経路 | 実装 | 拡張子チェックの入り方 |
|------|------|----------------------|
| ツリー列挙 `GET /api/md/tree` | `md/tree.ts` `listMdFilesForRepo()` | 通常ファイルは `path.extname === MD_EXTENSION` を直接判定。symlink は `resolveMdFileWithinRoot()` に委譲（解決後の実体パスで判定） |
| 読み取り `GET /api/md/file` | `api.ts` → `validateMdPath()` → `resolveMdFileWithinRoot()` | 検証ステップ 3（拡張子）で判定 |
| ライブ更新 WS `md_subscribe` | `md/watch.ts` `subscribe()` → `validateMdPath()` | 同上（HTTP と完全共有） |

**サーバ側の拡張子判定を緩和する変更は、`resolveMdFileWithinRoot` / `tree.ts` の判定 1 箇所ずつ（実質 `MD_EXTENSION` を拡張子集合に置き換えるのみ）で 3 経路すべてに波及する。**ライブ更新（chokidar の単一ファイル watch・refcount・1 クライアント 1 購読）は拡張子に依存しない実装のため、検証さえ通れば md 以外でもそのまま機能する。

### 1.2 パス検証（#63）と拡張子チェックの関係 — セキュリティ上の核心

`resolveMdFileWithinRoot()` の検証は 4 段:

1. `fs.realpathSync` で実在確認・symlink を実体まで解決
2. 解決後パスが repo ルート（realpath 済み）配下であること（**封じ込め判定**）
3. 拡張子が `.md`（**解決後の実体パス**に対して判定）
4. 実体が通常ファイルであること

**パストラバーサル防御はステップ 1–2（realpath 封じ込め）が担っており、ステップ 3（拡張子）とは独立している。したがって拡張子チェックの緩和は「repo ルート外への脱出」を一切広げない。**

ただし拡張子チェックは事実上の**コンテンツ許可リスト**として機能しており、緩和には別種の露出リスクがある（§2 で詳述）。

### 1.3 走査・除外ルール（#61/#65）

- `tree.ts` は `.` 始まり**ディレクトリ**（`.git` 含む）と `node_modules` を再帰から除外。`.` 始まりの**ファイル**は除外しない（`.hidden.md` は列挙対象、と明文化済み）。ただし `.env` 等の拡張子なしドットファイルは `path.extname(".env") === ""` のため現状は `.md` 判定で自然に落ちている。
- symlink は辿らない（ディレクトリ symlink はスキップ、ファイル symlink は読み取り API と同じ検証で列挙可否を判定 —「一覧に出る＝読める」の対称性維持）。
- ツリーはオンデマンド走査でツリー用 fs-watch は追加しない（#61 決定。本設計でも維持）。

### 1.4 file API（#66）とサイズ上限

- 404 一様応答（検証失敗・不存在・拡張子外を区別しない）、1MB 超のみ 413（`fs.stat` 先行判定で本文を読まない）。
- 応答は `c.json({ content })` の **UTF-8 文字列固定**。バイナリ（画像）はこの契約では返せず、別途バイナリ応答経路が必要（§3 Phase B）。

### 1.5 除外ルールと file API の既存の非対称（緩和で拡大する点）

file API（`validateMdPath`）は tree の除外ルール（ドットディレクトリ・`node_modules`）を**適用していない**。現状でも `.git/` や `node_modules/` 配下の `.md` はツリーに出ないが API では読める（読み取り側が寛容な片方向の非対称で、実害が小さいため許容されてきた）。拡張子を緩和するとこの非対称が「`.git/config` や `node_modules` 配下の任意ファイルが API で読める」に拡大するため、§2 の対策とあわせて扱う。

### 1.6 UI 側

- `FileTree.tsx`: サーバのフラット一覧からネスト表示を導出するだけで拡張子ロジックなし。変更は空状態メッセージ（「.md ファイルが見つかりません」）程度。
- `PreviewPanel.tsx`: 取得内容を無条件に react-markdown でレンダリングする。md 以外にはファイル種別に応じた表示分岐（§3）が必要。ライブ更新の購読・再フェッチ機構はファイル種別非依存でそのまま使える。

**結論: 実現可能。サーバ側の変更は局所的（拡張子集合の導入＋種別情報の応答追加＋画像用バイナリ経路）で、既存のパス検証・watch 機構はそのまま流用できる。主な設計判断はセキュリティ境界（§2）と UI の表示分岐に集中する。**

## 2. セキュリティ影響と対策（拡張子緩和の設計）

脅威モデルは既存決定を踏襲する: ローカル個人利用・127.0.0.1 バインド・Host/Origin 検証あり（`api.ts` の `isAllowedHost`/`isAllowedOrigin` が HTTP・WS 共通）。その上で拡張子緩和により新たに生じる露出は次の 3 点。

### 2.1 秘密情報ファイルの露出

`.env`・秘密鍵・トークンファイル等は現状 `.md` 制約で偶然守られている。対策（本設計の決定）:

- **無制限緩和ではなく拡張子アローリスト方式を維持する**。`MD_EXTENSION` を `PREVIEWABLE_EXTENSIONS`（種別カテゴリ付きの Map）へ置き換え、正本を引き続き `path-validation.ts` に一元化する。
- **拡張子なしファイルと `.` 始まりファイルは対象外**とする。この防御が構造的に落とせるのは `.env`・`credentials`・`id_rsa` のような**ドット始まり・拡張子なしのファイル名パターンに限る**（`Makefile` 等が見えない代償は許容）。
- 鍵系拡張子（`.pem`/`.key` 等）はアローリストに含めない。
- **残余リスク（受容）**: `credentials.json`・`config.yaml`・`token.txt` のように**許可拡張子を持つ秘密情報はアローリストでは防げない**。ファイル名 deny パターンや内容検査などの追加の秘密情報ポリシーは導入せず、既存の脅威モデル（ローカル個人利用・127.0.0.1・Host/Origin 検証。§2 冒頭）の下で残余リスクとして受容する。脅威モデルが変わる場合（リモート公開等）はその時点で別途ポリシーを設計する。

### 2.2 file API と除外ルールの非対称の拡大（§1.5）

対策（本設計の決定): 緩和と同時に、`validateMdPath` 系の検証へ**repo 相対パスのセグメント判定**（いずれかのセグメントが `.` 始まり、または `node_modules` なら拒否）を追加し、「ツリーに出ないものは読めない」方向へ対称性を揃える。判定は realpath 解決後の「ルートからの相対パス」に対して行う（symlink で除外ディレクトリへ潜る抜け道を塞ぐ）。

- 注: これは現状 `.md` で許容している非対称（`.git` 配下の md が読める）を**閉じる方向の変更**である。挙動変更として実装 PR で明示する。
- **`.` 始まり判定の統一（決定）**: ディレクトリセグメントに加え、**ファイル名セグメントも `.` 始まりなら列挙・読み取りとも対象外**とする（§2.1 の「`.` 始まりファイルは対象外」と同一ポリシーに一本化。「一覧に出る＝読める」の対称性を保つ）。現行実装は「`.` 始まりディレクトリのみ除外・`.hidden.md` ファイルは列挙・読み取り可」（§1.3）のため、これは**挙動変更**である。tree.ts の明文化コメント（`.hidden.md` を含める旨）の更新と、tree／file API 双方が同一挙動になることのテストを、実装 PR の受け入れ基準に含める。

### 2.3 応答 Content-Type 起因の XSS（Phase B の画像経路）

現行 API は JSON 応答のみで、リポジトリ内容がドキュメントとしてブラウザに解釈される経路がない。画像インライン表示でバイナリ応答経路を追加する際は:

- **Content-Type は拡張子アローリストからの静的マッピングのみ**で決定し、内容スニッフィングをしない。`X-Content-Type-Options: nosniff` を付与する。
- **`image/*` 以外は返さない**（`text/html` を返す経路を作らない）。
- **SVG はインライン画像の対象外**とし、テキスト（コード）として表示する。`<img>` 経由ならスクリプトは実行されないが、URL 直開きで board オリジン上でスクリプトが実行される経路になるため、埋め込みスクリプトを持ちうる SVG は画像経路に載せない。

### 2.4 変わらないもの

- realpath 封じ込め・404 一様応答・413 のみ区別、という #61/#63 の決定はそのまま維持する。
- 書き込み経路は一切追加しない（NFR-01。スコープ 2 は別 Issue — §4）。
- コマンドプリフィルの自動実行禁止・board 停止の非依存性（NFR-02）には影響しない。

## 3. 段階分け設計案（スコープ 1: 表示・プレビュー）

各フェーズは独立して価値を出せる単位で、上から順に実装する。フェーズ間で API 契約の後戻りが出ないよう、Phase A の時点で応答に種別情報を含める。

### API 契約の固定（Phase A で導入・全フェーズ共通）

`kind` の**正本（プロデューサー）は `GET /api/md/file` 応答のみ**とする。ツリー応答（`GET /api/md/tree`）はフラットなパス一覧のまま `kind` を持たず（#61 の「サーバはツリー構造を持たない」を維持）、UI の表示分岐は常に file API の応答で行う（UI が拡張子から種別を推測する分岐を持たせず、サーバのアローリスト定義との二重管理を避ける）。`kind` の語彙は Phase A の時点で 4 値すべてを予約定義する:

```text
GET /api/md/file?repo=<name>&path=<repo相対パス>
  → 200 { kind: "markdown", content: string }              # Phase A〜
  → 200 { kind: "text",     content: string }              # Phase A〜
  → 200 { kind: "image" }                                  # Phase B〜。本文は含めない（バイナリは /api/md/raw で取得）
  → 200 { kind: "binary", size: number, mtimeMs: number }  # Phase C〜。メタ情報のみ・本文非公開
  → 404（検証失敗・不存在・アローリスト外・除外セグメントは同一応答。現行方針どおり）
  → 413（検証通過後のサイズ超過のみ。テキスト系上限 1MB。現行どおり）

GET /api/md/raw?repo=<name>&path=<repo相対パス>            # Phase B 新設。画像バイナリ専用
  → 200 image/*（拡張子アローリストからの静的マッピング＋ X-Content-Type-Options: nosniff）
  → 404 / 413（判定方針は file API と同一。上限は画像 10MB）
```

UI の分岐: `markdown`/`text` は `content` を描画、`image` のときのみ `<img src="/api/md/raw?...">` を使い、`binary` はメタ情報を表示する。画像もクリック時はまず file API を呼び、`{ kind: "image" }` 応答を受けてから raw を参照する（種別判定の入口を file API に一本化）。

### Phase A: テキスト系プレビュー（コード・設定・ログ）

- **対象**: アローリストに登録したテキスト系拡張子（案: `.ts` `.tsx` `.js` `.jsx` `.json` `.jsonc` `.yaml` `.yml` `.toml` `.tsv` `.csv` `.txt` `.log` `.sh` `.py` `.css` `.html` `.svg` `.xml`。`.html`/`.svg` は**テキストとして**表示するだけで、ドキュメントとして解釈する経路は作らない）。確定は実装時。
- **サーバ**: `MD_EXTENSION` → `PREVIEWABLE_EXTENSIONS`（拡張子→カテゴリ `markdown | text` の Map）に置換。`GET /api/md/file` の応答を上記契約の `kind` 付き形へ拡張（`kind` 追加は後方互換。Phase A 時点で実際に返る値は `markdown | text` の 2 値）。§2.2 のセグメント除外判定を同時に導入。サイズ上限 1MB は据え置き。
- **UI**: `kind === "markdown"` は従来どおり react-markdown。`text` は既存依存の highlight.js（rehype-highlight が同梱）で直接ハイライトし `<pre><code>` 表示。ハイライト言語は拡張子から引き、未対応拡張子はプレーン表示。空状態メッセージを「表示できるファイルがありません」に変更。
- **ライブ更新**: 変更不要（検証共有により自動で対象拡大）。nvim でコード・設定を編集しながらのライブ確認がそのまま成立する。

### Phase B: 画像インライン表示

- **対象**: `image/png` `image/jpeg` `image/gif` `image/webp`（SVG は §2.3 により対象外・テキスト扱い）。
- **サーバ**: バイナリ応答の `GET /api/md/raw`（上記契約）を新設。検証は既存 `validateMdPath` 系を完全共有し、404/413 の応答方針も同一。Content-Type は静的マッピング＋`nosniff`（§2.3）。サイズ上限は画像のみ 10MB（仮置き。スクリーンショットが 1MB を超えるため。確定は実装時）。file API は画像に対し `{ kind: "image" }`（本文なし）を返すよう拡張する。
- **UI**: file API の `{ kind: "image" }` 応答を受けて `<img src="/api/md/raw?...">` で表示（本文の fetch はしない）。ライブ更新は `md_file_changed` 受信時に img の URL へキャッシュバスター（reload token）を付けて再読み込み。
- **tree**: 画像拡張子をアローリストに追加するだけ。

### Phase C: その他ファイルの情報表示（必要になったら）

- **対象**: アローリスト外も含む全ファイル（除外ルール適用後）をツリーに表示し、プレビュー不能なものはメタ情報（サイズ・更新日時）のみ表示。
- **サーバ**: tree の拡張子フィルタ撤廃＋file API に stat ベースのメタ情報応答（`kind: "binary"`）を追加。**読み取り本文 API はアローリスト外を引き続き 404 にする**（§2.1 の秘密情報対策を本文非公開のまま保つ。メタ情報のみ返す）。
- **判断**: Phase A/B 運用後に「ツリーに見えないことが実際に困るか」を見てから着手する（YAGNI）。Phase C を実装しない選択もあり得る。

### 段階分けに共通の決定

- **API ルート名・WS メッセージ種別（`/api/md/*`・`md_subscribe` 等）は改名しない**。消費者は同一リポジトリの UI のみだが、`md` プレフィックスは歴史的経緯として全経路で整合しており、改名は差分を膨らませるだけで挙動価値がない。ドキュメント（本ファイル・markdown-preview.md）に「md は歴史的名称で現在は対象拡張子が広い」と注記する。
- 拡張子アローリストの**設定化（ユーザー設定での増減）はしない**。コード内固定で開始し、要望が出てから検討する（YAGNI。Issue 本文の「緩和 or 設定化」に対する決定）。

## 4. スコープ 2（D&D/コピペ配置・削除）の別 Issue 切り出し案

スコープ 2 は**書き込み系 API の新設**であり、読み取り拡張（スコープ 1）とはリスク・設計論点が非連続なため、別 Issue に切り出す（Issue #117 の「進め方（案）」どおり）。本節はその起票素材。

### 位置付けの整理（設計原則との関係）

- NFR-01（board は**状態ファイル**＝台帳・journal・memory・runs.jsonl に書き込まない）が禁じるのは状態ファイルへの書き込みであり、一般ファイルの配置そのものではない。既に `POST /api/fleet/agents`（#122）が fleet.tsv（board 自身の manifest）への書き込み系 API として存在し、先例がある。
- ただし「書き込みはターミナル内の Claude Code セッション経由」という設計原則 1 の趣旨からは逸脱方向の拡張であり、**採否自体を人間が判断すべき論点**として Issue に明記する。

### 提案スコープ（切り出す Issue の内容案）

1. **配置（アップロード）**: Finder からツリーへの D&D、およびペースト（クリップボードのファイル/画像）。`POST /api/files?repo=&path=`（仮称）。
2. **削除**: ツリーのコンテキストメニューから。`DELETE /api/files?repo=&path=`（仮称）。

### ガード方針（Issue に含める設計制約案）

- **パス検証は読み取りと同じ realpath 封じ込め**を必須とし、加えて:
  - **状態ファイル・board 管理ファイルへの deny-list**（challenge-ledger.md・journal・memory/・runs.jsonl・fleet.tsv・`.git/` 配下等）を書き込み経路にのみ導入する（NFR-01 をコードで強制）。
  - 配置先の親ディレクトリは既存に限る（API 経由の暗黙 mkdir はしない）。ドットセグメント・`node_modules` 配下は読み取り同様拒否。
- **TOCTOU（検証と操作の間の競合）対策**: realpath による事前検証は既存ファイルの読み取りには適するが、書き込みでは不十分。新規アップロードの最終パスは検証時点で存在せず realpath 検証が効かないうえ、検証後〜実操作までの間に最終要素を symlink へ差し替えられると検証済みパス外を操作しうる。実操作は**最終要素の symlink を追従しない方式**を必須とする: 作成は `O_CREAT | O_EXCL`（上書き許可フラグ時は一時ファイル書き込み→ `rename` の原子的置き換え）、削除は直前の `lstat` で通常ファイルであることを確認してから `unlink`（symlink そのものは拒否）。symlink 置換シナリオのテストを受け入れ基準に含める。
- **上書きはデフォルト拒否**（既存パスへの POST は 409。明示フラグでのみ許可）。
- **削除は不可逆操作としてガード**: UI 確認ダイアログ必須（削除対象パスの明示）。ゴミ箱（OS trash）経由にできるなら unlink より優先。ディレクトリ削除は対象外（ファイルのみ）。
- サイズ上限・拡張子制限は読み取り側アローリストと整合させる（プレビューできないものを置ける非対称を作らない）。
- 書き込み系 API は既存の Host/Origin 検証に加え、**Origin ヘッダ必須**（非ブラウザ直叩きでの CSRF 面を狭める）を検討する。

## 5. 置いた仮定・意思決定（サマリ）

| # | 決定 | 根拠 |
|---|------|------|
| 1 | 拡張子は無制限緩和ではなくアローリスト方式を維持。許可拡張子を持つ秘密情報（`credentials.json` 等）は防げない残余リスクとして受容 | ドット始まり・拡張子なしパターンの構造的防止＋脅威モデル準拠（§2.1） |
| 2 | 拡張子なし・`.` 始まりファイルは**列挙・読み取りとも対象外**に統一（現行の `.hidden.md` 列挙・読み取り可からの挙動変更） | §2.1 の防御と「一覧に出る＝読める」対称性の両立（§2.2） |
